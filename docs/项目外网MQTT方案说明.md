# 外网数据通道部署指南（MQTT 方案）

> 目标：这块屏被带到公司、酒店、出差所在地时，只要**能上网**，就能继续显示家里 HA 的全部数据。

---

## 一、为什么不用 Native API 直连

| 方案 | 数据方向 | 屏幕出门后能否用 |
|---|---|---|
| **Native API（原方案）** | HA **主动连** ESP32:6053 | ❌ 不能。设备在外网没有公网 IP，路由器也做不了端口映射，HA 根本连不上它 |
| **MQTT（本方案）** | ESP32 **主动连** broker | ✅ 能。只要设备能上网 + 能连到 `home.example.top:1883` |

关键点：ESPHome 的 `platform: homeassistant` 传感器（原来那 50 个）**硬依赖 Native API**，官方文档明确写了 "using the native API"。所以不改不行。

**改造后数据流：**

```
HA 自动化（每 5 秒）
   │  读 50 个实体 → 拼成 1 个 JSON
   ▼
mqtt.publish → home/ha-monitor-display（retain=true）
   │
   ▼
你的 Mosquitto broker（home.example.top:1883）
   │
   ▼
ESP32 订阅该主题 → 解析进 hd_* 全局变量
   │
   ▼
49 个 template 传感器（1 秒刷新）→ 三页 lambda 读取
```

**最大的好处**：三页的 lambda、布局、字体**一行都没改**。因为 template 传感器的 `id` 名称和原来的 `platform: homeassistant` 完全一致，类型也对得上（`Sensor*` / `BinarySensor*` / `TextSensor*`）。

## 三、HA 侧部署（约 5 分钟）

### 3.1 确认 packages 已启用

编辑 `/config/configuration.yaml`，确认有这两行：

```yaml
homeassistant:
  packages: !include_dir_named packages
```

如果已经有 `homeassistant:` 段，把 `packages:` 加进去即可（注意缩进）。

### 3.2 放入自动化文件

```bash
# 在 HA 里，用 File Editor / Samba / SSH 都行
cp monitor_display_push.yaml /config/packages/monitor_display_push.yaml
```

### 3.3 重启 + 验证

1. **开发者工具 → YAML → 检查配置**，应无报错
2. 重启 HA
3. **开发者工具 → 状态**，搜索 `monitor_display_push`，确认自动化存在且为 `on`
4. 用 MQTT 工具（见下）订阅 `home/ha-monitor-display`，应在 5 秒内收到一帧 JSON

**验证 JSON 的快捷方法**（HA 的 MQTT 集成自带）：

> 设置 → 设备与服务 → MQTT → 配置 → **监听主题** → 输入 `home/ha-monitor-display` → 开始监听

正常输出类似：

```json
{"ts":1761700000,"fan1_rpm":1200.0,"fan2_rpm":1150.0,...,"weather":"sunny","stock":"上证 3120.5"}
```

> **如果字段值是 `null`**：说明那个实体在 HA 里是 `unavailable` 或实体名不对。
> 屏幕端会显示 `--`，不影响其他字段。

## 四、ESPHome 侧部署

### 4.1 补 secrets.yaml

在主配置同目录的 `secrets.yaml` 里确认有：

```yaml
mqtt_broker: home.example.top
mqtt_username: your-mqtt-username
mqtt_password: "你的MQTT密码"
```

> 仓库上传版已把 broker 地址与用户名一并收进 `secrets.yaml`（`mqtt_broker` / `mqtt_username`），
> 自用时填你自己的值即可。

### 4.2 编译上传

```bash
esphome run ha-monitor-display.yaml
```

### 4.3 看日志确认

正常应该看到：

```
[I][mqtt:xxx]: Connecting to MQTT...
[I][mqtt:xxx]: MQTT Connected!
[D][ha_data:xxx]: 收到数据帧 ts=1761700000
```

如果一直看不到 `收到数据帧`，说明没订阅成功，检查：
- broker 地址/端口/账号密码
- HA 自动化是否真的在跑

## 五、离线指示说明

屏幕右上角新增了一个状态提示（只在数据不可信时出现）：

| 状态 | 表现 |
|---|---|
| 正常 | 什么都不显示 |
| 超过 15 秒没收到新数据 | 右上角显示 🔴 `离线` + 断云图标 |

**为什么这样设计**：`WiFi 连着` 不等于 `数据可信`。broker 挂了、HA 停了、家里断网了，这三种情况下 WiFi 可能都是通的，但屏幕上的数字已经过期。所以判据用「数据新鲜度」而不是「WiFi 状态」。

开机后前 20 秒不显示离线提示，避免开机瞬间闪一下红字。

## 六、需要注意的取舍

### 6.1 在家时也有 0~5 秒延迟

因为数据要绕一圈：HA → broker → 屏幕。原来走 API 是毫秒级。

- 温度、NAS 指标、风扇转速这类慢变数据：**没感觉**
- 如果将来要做「点屏幕立刻开灯」这类实时控制：会有延迟感

> 后续如果觉得延迟不可接受，可以在现有结构上**叠加** API 通道（把 API 传感器的值也写进同一个 `ha_data` 结构体），页面完全不用改。现在先不加，保持简单。

### 6.2 双向控制暂时没做

原来 `switch` / `number` 是 HA 可以控制的（比如屏幕熄屏超时）。
改造后这些**仍然是本地实体**，通过 MQTT discovery 暴露给 HA 的能力被关掉了（`discovery: false`）。

如果你需要从 HA 远程调屏幕亮度/休眠，告诉我，可以单独开这条通道。

### 6.3 1883 明文的安全问题

你选择了先用 1883 明文跑通。这里提醒一句现状：

> 公网暴露 1883 + 明文密码 = 任何人扫到你的端口就能拿到 broker 的用户名和密码，进而控制你**全屋** MQTT 设备（包括门锁、开关）。

跑通之后**强烈建议**升级到 8883 + TLS，成本很低：
1. Mosquitto 加载项里放证书（Let's Encrypt 或自签）
2. 路由器把 1883 映射改成 8883
3. 主配置里改 `port: 8883` 并加 `certificate_authority:`

我可以在你验证通过后帮你做这一步。

## 七、排障清单

| 现象 | 排查方向 |
|---|---|
| 屏幕一直显示 `离线` | broker 连不上：检查域名解析、端口映射、账号密码 |
| 部分字段显示 `--` | 那个 HA 实体是 `unavailable`，或实体 ID 写错了 |
| 开关类字段恒显示"关" | 见下方「开关字段的三态处理」 |
| 数据不更新但图标没出现 | 检查 `ha_data_last_ms` 是否在增长（看日志） |
| 编译报 `struct` 相关错误 | 确认 ESPHome 版本 ≥ 2024.6 |
| 时间显示不对 | SNTP 需要能访问外网 NTP（已配阿里云 + cloudflare 三个源） |

### 开关字段的三态处理

早先开关类字段用的是 `1 if is_state('xxx','on') else 0` 写法，这个写法有个坑：
**实体 ID 拼错时 `is_state()` 不报错，只是返回 False**，于是屏幕上安静地显示"关"，
看起来像"设备确实关着"，实际是"根本没读到"。语音、在线设备 A/B、已连接时长、
进扇/出扇 这几处就都栽在这上面。

现在改成三态：

| HA 侧 | JSON 值 | ESP32 侧 | 屏幕显示 |
|---|---|---|---|
| 实体不存在 / `unknown` / `unavailable` | `null` | `-1`（不发布） | `--` |
| `off` | `0` | `0` | 关 / 离线 |
| `on` | `1` | `1` | 开 / 在线 |

对应实现：
- HA 侧 `monitor_display_push.yaml` 里定义了 Jinja 宏 `sw(eid)` 统一处理；
- ESP32 侧 `hd_*` 开关全局变量是 `int8_t`（-1/0/1），`binary_sensor` 模板在
  `hd_* < 0` 时不发布，于是 `has_state()` 保持 false，UI 就能显示 `--`。

**看到 `--` 就是在告诉你"这个实体没找到"**，去 HA 的「开发者工具 → 状态」
搜一下真实实体 ID，改 `monitor_display_push.yaml` 里对应的那行即可。

### 字体 bpp 参数

`ui_common.yaml` 里每个字体都有 `bpp`（bits per pixel），控制字形的灰度档位：

| bpp | 灰度档位 | 效果 |
|---|---|---|
| 1 | 2 档（黑白） | 明显锯齿，不推荐 |
| 2 | 4 档 | 12px 尚可，16/20px 边缘偏毛糙 |
| **4** | **16 档** | **当前值，边缘平滑，TFT 上最接近"锐利"** |
| 8 | 256 档 | 肉眼已看不出比 4 好，纯浪费 Flash |

它只影响字形位图体积，不影响字体文件、不影响任何逻辑。本项目实测规模
（624 字形 × 3 档 CJK 字体 + 47 图标 × 3 档 MDI 字体）：

| 字体 | bpp2 | bpp4 | 增量 |
|---|---:|---:|---:|
| ui_font_small (12px) | 24.3K | 47.3K | +23.0K |
| ui_font_medium (16px) | 40.5K | 81.1K | +40.5K |
| ui_font_large (20px) | 62.9K | 123.9K | +60.9K |
| mdi_icons (16px) | 3.3K | 6.6K | +3.3K |
| mdi_icons_12 | 1.9K | 3.9K | +1.9K |
| mdi_icons_20 | 5.0K | 10.1K | +5.0K |
| **合计** | **138K** | **273K** | **+135K** |

16MB Flash 下占比从 0.8% 升到 1.7%，完全无压力，所以直接用了 4。

### 图标与文字的垂直对齐（16px 行）

屏幕上一共有两种字号的"图标 + 文字"组合：`ui_font_small`(12px) 和
`ui_font_medium`(16px)。图标原来统一用 `mdi_icons`(16px)，在 16px 行上
**偏小且偏上**，原因是两个字体在 LVGL 里的行框高度不一致：

| 字体 | size | hhea 行高倍率 | LVGL line_height |
|---|---:|---:|---:|
| materialdesignicons | 16 | 1.000 | **16.0 px** |
| NotoSansSC | 16 | 1.448 | **23.17 px** |

`align: left_mid` 是让 **label 控件**在父容器里居中，而 label 高度取的是
字体行高。图标 label 高 16、文字 label 高 23.17，两者顶边对齐的位置不同，
字形墨迹（真正画出来的像素）自然就错开了。

实测各字形墨迹（size=16，相对 label 中心）：

| | 墨迹高度 | 墨迹中心 |
|---|---:|---:|
| 汉字 `语` | 14.78 px | −1.01 |
| mdi `home-account` | 11.34 px | +0.33 |

→ 图标比汉字**小约 23%**，中心**偏上 1.3px**，视觉上就是"又小又靠上"。

#### 解决办法：图标升到 20px + label 高度收到 18

LVGL 在 `left_mid` 下算纵向偏移用 `y += ph/2 - h/2`，`h` 是 label 高度。
把图标 label 的 `height` 显式设成 18（小于 20 的行高），label 会以 18px
的框居中，而字形仍按 20px 渲染，等于把字形相对上移了。

最终 16 组图标/文字的实测偏差（相对汉字墨迹中心）：

| 位置 | 偏差 | 图标高/文字高 |
|---|---:|---:|
| 概览 行1 天气 | −0.53 | 120% |
| 概览 行2 在家 / 客人 / 手机 / 语音 | −0.29 / +0.10 / +0.13 / −0.01 | 94~122% |
| 概览 行3 居家 / 车位 | −0.29 / +0.02 | 94% / 88% |
| 概览 在线设备 A / B（原 Nova13/12） | −0.05 | 155%（字母矮，正常） |
| 网络 行1 外网IP / 已连接 | +0.12 / −0.13 | 100% / 122% |
| 系统 行1 系统 / 运行 | +0.03 / +0.14 | 101% / 113% |
| 系统 行2 SSID / IP | −0.06 / −0.05 | 122% / 127% |

**平均绝对偏差 0.15px，14/16 组在 ±0.35px 内**，肉眼已看不出高低差。

两个需要单独微调的（字形本身墨迹不对称）：

```yaml
# 概览页 行3 车位（mdi:car，轮子在底部，重心偏上）
text_font: mdi_icons_20
height: 18
y: -1
```

水平方向同步调整了：图标从 16px 升到 20px 后占位变宽（advance 16→20），
右边文字相应右移 1~4px，保持原来 0~8px 的视觉间隙不变。

> 只改了配 **16px 文字** 的 16 个图标；配 12px 文字的 41 个图标保持
> `mdi_icons`(16px) 不动，因为那批本来就基本等高。

### 离线指示图标

MQTT 数据通道断开时，右上角显示断云图标 + "离线"两字：

```yaml
- label:
    id: offlink_icon
    align: TOP_RIGHT
    x: -9          # 比原 -6 左移 3px
    y: 6
    text: "\U000F1BF6"   # mdi:cloud-off（实心断云）
    text_font: mdi_icons_12
- label:
    id: offlink_text
    align: TOP_RIGHT
    x: -26         # 与图标保持 5.5px 净间距
    y: 4
    text: "离线"
    text_font: ui_font_small
```

> 字形码位说明：MDI 23.9 版本里 `mdi:cloud-off` 是 **U+F1BF6**，
> 常见的 U+F0163 在这个版本里其实是 `cloud-outline`（描边云），换成
> U+F1BF6 才是实心断云。

### 数值单位与颜色约定

网络页「行3 左列」的四个计数带单位，因为它们是"在线几台 / 几个"，
带单位才是完整的中文句子；而「行2」那五个（主机 / 网关 / 无线 / 设备 / 语音）
数字本身即答案，不加单位：

| 位置 | 文案示例 | 单位 |
|---|---|---|
| 行2 主机 / 网关 / 无线 / 设备 / 语音 | `主机:3` | 无 |
| 行3 路由在线 | `路由在线: 4台` | 台 |
| 行3 控制设备 | `控制设备: 2个` | 个 |
| 行3 终端在线 | `终端在线: 28个` | 个 |
| 行3 低电量数 | `低电量数: 1个` | 个 |

带单位后最长的文案是 `路由在线: 999台`，12px 下实测 **87.9px**，
右沿 112.9px，距左列容器右边界 155px 还有 42px 余量，不会挤到中列。

无数据时只显示 `路由在线: --`（不带单位），这样一眼能区分
"数据没到"和"数值是 0"。

**颜色**：百分比类（CPU / 内存）的常态色与该行的图标颜色一致，
方便视觉上归组；超阈值时才切成警示色：

| 项目 | 常态（同图标） | 预警 | 危险 |
|---|---|---|---|
| CPU利用 | `0x6FE3C4` 绿 | ≥70% `0xFFD54F` 黄 | ≥90% `0xFF5252` 红 |
| 内存可用 | `0xC5A3FF` 紫 | ≥75% `0xFFD54F` 黄 | ≥92% `0xFF5252` 红 |

> **注意标签措辞**：这个位置显示的数值来自
> `sensor.lamnas_ws_memory_usage_real`，语义是**已用率**，但界面文案写的是
> 「内存可用」。所以数值 46% 读作「内存已用 46% / 还剩 54%」才正确，
> 阈值 75/92 也是按已用率定的。
>
> 如果希望字面与数值一致，把 `page_network.yaml` 里两处
> `"内存可用"` 改成 `"内存利用"` 即可（和 `CPU利用` 对齐）。
> 本次只改颜色，文案未动。

### 文案格式统一（分隔号后加空格）

早期各页的数值标签写法不统一，有 `主机:3`、`网关:--` 这种冒号后不带
空格的，也有 `路由在线: 4台` 带空格的。冒号后不带空格时，中文冒号与
数字挤在一起，12px 下几乎黏成一团。现已全部统一为 **`名称: 值`**
（半角冒号 + 一个空格）：

| 改前 | 改后 |
|---|---|
| `主机:3` | `主机: 3` |
| `网关:--` | `网关: --` |
| `循环:12ms` | `循环: 12ms` |
| `亮度:80%` | `亮度: 80%` |
| `PSRAM:3900K` | `外存: 3900K` |

无数据时的 `名称:--` 也一并改成 `名称: --`，保持视觉宽度稳定
（否则数值来/走时文字会横向抖动一下）。

### 系统页「外存」是什么

`外存` 显示的是 **PSRAM 剩余量**（`heap_caps_get_free_size(MALLOC_CAP_SPIRAM)`），
不是 Flash，也不是 SD 卡。

改成「外存」是为了和上一行「内存」（`debug.free` 的普通堆）在
4 个汉字的宽度内区分开——原来写 `PSRAM:` 是 6 个拉丁字符，
在 12px 下比相邻行宽一截，左侧竖排看起来参差不齐。

- **内存** = 内部 SRAM 空闲
- **外存** = PSRAM 空闲（本板 N16R8，8MB octal PSRAM）

两者都是"剩余量"，掉得快时都值得警惕，但量级差很远：
内部 SRAM 通常剩 100~300K，PSRAM 剩 3~7MB。

### 系统页右列的四个参数

| 行 | 标签 | 取值来源 | 无数据时 |
|---|---|---|---|
| 1 | `RSSI` | WiFi 信号强度，dB | `RSSI: --` |
| 2 | `WiFi` | 是否拿到 IP | `WiFi: --` |
| 3 | `MQTT` | MQTT 客户端连接状态 | `MQTT: 断开`（红） |
| 4 | `SIGQ` | 按 RSSI 分档的定性描述 | `SIGQ: --` |

SIGQ 三档：`> -55dB` 优秀 / `> -70dB` 良好 / 其余 微弱。
第 1 行已给出 dB 数值，第 4 行只做定性，避免重复。

> 这两行用的是 `mqtt::global_mqtt_client->is_connected()`，
> 直接读 ESPHome 的 MQTT 组件状态，不依赖 HA 侧推送。所以
> **即使 HA 没在推数据，这一行也能正确反映通道是否活着**，
> 排障时先看这里。

## 八、通知通道（2026-10-30 新增）

### 8.1 主题规划

| 用途 | 主题 | retain |
|---|---|---|
| 数据帧（每 5s） | `home/ha-monitor-display` | true |
| **通知（即时）** | `home/ha-monitor-display/notify` | **false** |
| 滚动新闻（预留） | `home/ha-monitor-display/news` | — |

通知是"即时"语义：**发布端不要开 retain**，重连不补发旧通知（数据帧才需要 retain 补帧）。

### 8.2 载荷格式

```json
{"title": "门铃", "message": "有人按门铃", "ts": 1761787200}
```

- `title` 可省（屏幕显示"通知"）；`ts` 是 Unix 秒，屏幕按本地时区显示 `MM-DD HH:MM`
- 设备侧 UTF-8 安全截断：标题 96 字节 / 正文 480 字节
- **emoji / 图片链接必须在发布端处理掉**（屏幕字库无 emoji 字形）——NR 子流程自动完成：
  剥 emoji（含 ⌛⏰⏱ 等符号区）、markdown/HTML 图片/链接、裸 URL；保留换行
- 正文字数：发布端按 UTF-8 字节截断到 460B（尽量在行边界收尾），设备端再兜底 480B 截断
- 正文含 `°C`、`µg/m³`、`｜` 等符号，已在 ui_font_notify 字库中（2026-10-30 补）

### 8.3 发布端：Node-RED 子流程（推荐）

导入 `NR子流程-屏幕推送.json`，首次使用在 mqtt out 节点里选好 Mosquitto broker。
之后任何节点输出接上即可：取 `msg.title` / `msg.message`（缺省回退 `msg.payload`）。

### 8.4 屏幕侧行为

- 收到通知 → 写入 8 条环形缓冲 + 未读数 +1
- 右上角铃铛（常显，所有页面可见）：无未读灰色 `bell`，有未读琥珀色 `bell-badge`，点击进通知页
- 通知页显示最新 4 条（标题 + 时间 + 正文两行），进入即清未读；底部「返回」键回概览页
- 通知正文用独立的全量常用字字体 `ui_font_notify`（GB2312 一级 3755 字 + ASCII + 中文标点，12px/bpp4，约 310KB）——**通知内容不再需要维护字库白名单**，固定 UI 的白名单机制保持不变
