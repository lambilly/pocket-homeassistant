## 一、结论先行

| 项 | 判断 |
|---|---|
| 技术可行性 | 无阻塞项，全部是已有模式的复用 |
| 素材完成度 | UI 布局 ~85%、NR 子流程 100%、数据通道 0%、字库 0% |
| 真正的新增成本 | **字库 310KB（GB2312 一级全量）** + 一条 MQTT 订阅链路 + 一个页面入口 |

一句话：**功能不是难点，"通知从哪进、消息长什么样、字够不够"这三件事定清楚了就基本写完了。**

## 二、现有素材盘点

### 已完成（`page_notify.yaml`，9.8KB）

- 4 个通知槽（y=39/100/161/222，高 59），每条含 标题 / 时间 / 正文 三个 label
- 顶栏「通知 + 共 N 条」、空态「暂无通知」、底栏「返回」
- 1s 巡检 lambda：从 8 槽环形缓冲按 newest-first 取 4 条渲染，时间戳 `ESPTime::from_epoch_local` 转 `MM-DD HH:MM`
- `on_load` 里清未读、置 `ui_current_page = 4`

### 已完成（`NR子流程-屏幕推送.json`）

- 兼容三种上游接线（msg.message / HA action 输出 / msg.data）
- 清洗：emoji、markdown 图片链接、HTML 标签、裸 URL 全部剥掉（屏幕无此字形）
- UTF-8 字节安全截断 460B，优先回退到行边界
- 输出 `{"title","message","ts"}` → `home/ha-monitor-display/notify`，QoS1，retain=false

### 完全缺失

1. `ui_font_notify`（12px，GB2312 一级 3755 字）——**唯一的大工程**
2. 主配置里 notify 主题的订阅与解析
3. `g_notify_*` 系列 globals（8 槽 × title/msg/ts + count/head/unread）
4. 页面入口（铃铛或第 4 键）与未读角标
5. 页面未注册进 `packages`，真机 `ui/` 里也没有这个文件

## 三、数据链路（四层）

```
① 触发源（任意）
   HA 自动化 / Node-RED / 手动 mqtt.publish
        │
        ▼  ② MQTT  home/ha-monitor-display/notify   QoS1  retain=false
   payload = {"title":"门磁","message":"前门已打开","ts":1761980000}
        │
        ▼  ③ 设备端 mqtt.on_json_message（新增第二个触发器）
   写环形缓冲：g_notify_title[8] / g_notify_msg[8] / g_notify_ts[8]
   head=(head+1)%8，count=min(count+1,8)，unread++，rev++
        │
        ▼  ④ 通知页 1s（或 rev 变化时）巡检 → 刷新 4 个槽 + 顶栏计数
```

### 3.1 HA 侧两种推法

**A. Node-RED（推荐，已有成品）**：导入 `NR子流程-屏幕推送.json`，选 broker，上游任何节点接进来即可。清洗和截断都在子流程里。

**B. HA 原生（轻量，不装 NR 也能用）**

```yaml
# packages/monitor_display_notify_push.yaml 片段
- alias: 屏幕通知推送
  trigger: ...
  action:
    - mqtt.publish:
        topic: home/ha-monitor-display/notify
        qos: 1
        retain: false
        payload: >-
          {{ {'title': title, 'message': msg, 'ts': now().timestamp()|int} | to_json }}
```

注意：原生推法**没有 emoji/链接清洗**，长文本也不截断。建议在 HA 侧套一层宏或在设备端做长度保护（见风险 4）。

### 3.2 设备端配置要点

```yaml
mqtt:
  on_json_message:
    - topic: home/ha-monitor-display          # 现有数据帧，不动
      then: ...
    - topic: home/ha-monitor-display/notify   # 新增
      then:
        - lambda: |-
            if (!x["message"].is<const char *>()) return;
            ...
```

- MQTT 主题是**精确匹配**，`home/ha-monitor-display` 不会收到子主题的消息，两条互不干扰
- 现有数据帧约 900B 已经跑通，notify 上限 460B 更小，**不需要动缓冲区配置**
- `on_json_message` 的列表写法与 `on_message` 同机制，理论支持；若编译报错，退回 `on_message` + `esphome::json::parse_json` 手解析

## 四、内存与字库账

### 4.1 RAM

| 项 | 大小 |
|---|---|
| 8 槽 × (title ≤24 字 + msg ≤460B) | ≈ 4 KB |
| 计数器 / unread / rev | 十几字节 |
| 页面控件（4 槽 = 12 label） | < 4 KB |

设备有 8MB PSRAM，`std::string` 走堆，**完全不构成约束**。

### 4.2 Flash（这才是真账）

`ui_font_notify`：12px、bpp4、GB2312 一级 3755 字

- 单字形 ≈ 12×12×4bit = 72B，加索引开销 ≈ 82B
- 3755 × 82B ≈ **308KB**
- 加上原有的三档白名单字体（≈130KB）和 MDI（≈40KB），字体总量约 480KB

**分区判断**：16MB Flash 的 ESP32-S3，Arduino 默认方案 app 分区约 6.25MB，当前固件估算 2MB 上下，加 310KB 无压力。第一次编译时看一眼 partition table 确认。

**代价**：编译时间会明显变长（3755 字形逐个渲染），预计比现在多几分钟，且只影响首次/字表变动后。

### 4.3 字表要补的白名单字

已核对现有 327 字表：`知`（通知）、`返`（返回）**缺失**；`通/共/条/暂/无` 已有。`铃` 若做角标文本也要补（用 MDI 图标则不缺）。

## 五、页面结构（现有稿的改造点）

| 现状 | 问题 | 建议 |
|---|---|---|
| 4 槽固定，缓冲 8 条 | 后 4 条永远看不到 | M1 先 4 槽；M4 再决定要不要滚动（8 槽放滚动容器） |
| 1s 无条件重设 12 个 label | 每秒 12 次 `lv_label_set_text`，LVGL 会重排+刷屏，白耗 SPI | 加 `g_notify_rev` 计数器，只有新消息或进页时才刷 |
| 卡片色写死 `0x1E1E1E` / 页面底 `0x121212` | v1.1.0 已改 HA 下拉选色，写死会跟其他页不一致 | 新增 `ui_bg_notify` + 第 4 个 select「Notify Bg Color」，或用固定深色并在文档里说明 |
| 文字色 `0xE0E0E0` / `0xBDBDBD` | 违反 v1.1.0 白字规则 | 标题正文改 `FFFFFF`，时间留 `757575` |
| `long_mode: DOT` | 现有三页没用过这个选项，未经验证 | 首次编译后真机看一眼截断是否正常，异常就改回固定 `width` + 手动截断 |
| 正文区高 36px | 12px 字体约 3 行，约 110 个汉字；NR 上限 460B ≈ 153 汉字 | 可接受，末尾会截断；若要完整显示需增大槽高或做详情页 |

y39  h59  槽1    标题(12px 白)     时间(12px 灰)
                 正文第1行 / 第2行 / 第3行 (12px 白)
y100 h59  槽2
y161 h59  槽3
y222 h59  槽4
y286 h29  底栏   返回（或改 4 键 TAB，见下节）

## 六、入口与导航：三个方案（**需你拍板**）

### 方案 A：改 4 键 TAB（`家居 | 网络 | 系统 | 通知`）

- 3 个页面各把现有 3 label 扩成 4 label（每个 117 宽），当前页仍用青色 `4FD8FA`
- 通知页也用同一套 4 键 TAB，去掉底栏「返回」
- 未读角标：TAB 的「通知」右上角一个 6px 红点（`FF5252`）
- 优点：入口永远可见、无隐藏页、四页结构一致、不需要往 top_layer 塞悬浮图标
- 代价：3 个页面的 TAB 行要重排（你之前对 TAB 的 x 偏移非常敏感，这行改完必然要再调一轮像素）

### 方案 B：铃铛悬浮（原设计稿）

- `top_layer` 右上角放 bell 图标 + 未读红点，任意页可点进通知页
- 通知页底栏「返回」回家居页
- 优点：不动三页布局，改动面最小
- **致命问题**：三页的行 1 卡片（y5 h50）右端都有内容（上证指数 / 内网IP / 运行组），top_layer 悬浮图标会直接盖在上面。除非把铃铛放在卡片内的空白处，那就得逐页挪元素

### 方案 C：铃铛并入行 1

- 每页行 1 右端腾出 ~26px 给铃铛，右侧现有元素左移
- 优点：不悬浮、不遮挡
- 代价：3 页行 1 都要动，且行 1 是最挤的一行（你刚花了一轮调左右边界对齐）

**我的判断：选 A。** 理由是 B 有硬伤（遮挡）、C 要动最敏感的行 1，而 A 虽然要重排 TAB，但 TAB 是一整行独立控件、四个等宽块、改动可预测，且顺手解决了「通知页是否需要返回键」的问题。且 A 的四页结构对未来再加页也更干净。

## 八、风险清单

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | `on_json_message` 列表写法不被支持 | 编译失败 | 退回 `on_message` + `parse_json()` |
| 2 | `long_mode: DOT` 未在本项目验证过 | 标题截断异常 | 真机看一眼，异常改手动截断 |
| 3 | 3755 字库编译时间暴涨 | 迭代变慢 | 字库一次性做完，后续不再动；改文案时只改白名单三档字体 |
| 4 | HA 原生推法不清洗长文本 | 超出 460B 时设备端截断或花屏 | 设备端做硬截断（按字节、避半个汉字） |
| 5 | retain=false + 无持久化 | 断电重启后通知清空 | 可接受；若要保留改用 NVS 存 1 条「最新」 |
| 6 | QoS1 可能重复投递 | 同一条重复入缓冲 | payload 带 `ts`，与上一条 ts+title 相同则丢弃 |
| 7 | 通知页静态 1s 轮询 | 无效刷屏耗电 | 改用 `g_notify_rev` 变化触发 |
| 8 | 睡眠中收到通知 | 屏幕不亮，用户不知道 | 加开关「通知亮屏」（默认关，省电）；至少让角标在唤醒后可见 |

## 十一、六种通知模式的实测形态（11-01 用户提供截图）→ 方案修正

### 11.1 形态归纳

| 模式 | 结构 | 体量（估） | 特征 |
|---|---|---|---|
| 系统音量 | 4 个【】字段 + 一张**两列**音量表 | ~200 字 / 8 行 | 表格依赖对齐 |
| 居家模式 | 4 个字段 + 【模式说明】5 行 + 【房间情况】3 行**两列** | ~300 字 / 14 行 | 两列布局 |
| 语音指令 | 【识别结果】5 行 + 【所有响应】+ 【人体感应】两列网格 | ~250 字 / 12 行 | 两列网格 |
| 新闻简报 | 日期抬头 + **15 条编号列表** + 微语 | ~1500 字 / 30+ 行 | 需要 2~3 屏 |
| 家居简报 | 5 大段（活动/运行/电器/能耗/费用/物业/余额） | ~2000 字 / 40+ 行 | 需要 3~4 屏 |
| 天气预报 | 天气/室内/室外/明天 四段 + 配图 | ~600 字 / 25 行 | 含图片 |

共同点：**标题 = emoji + 2~4 字；正文是预排版纯文本，用【】分段、emoji 当彩色状态标记；末尾相对时间「1分钟前」；底部有「忽略」动作。**

### 11.2 与原设计的冲突

原 `page_notify.yaml` 是「4 槽 × 2 行预览，460B 上限」，对应的是短消息（门磁/传感器）。这六种模式里 **4 种是长报告**，460B 连新闻简报的 1/6 都放不下，2 行预览只能看到开头一句，等于没读到内容。

必须改三处：

1. **容量**：单条上限 460B → **4KB**（家居简报 UTF-8 约 3.3KB）。8 槽 × 4KB ≈ 32KB，PSRAM 无压力；但 MQTT 客户端缓冲要跟着放大（需实机验证，必要时降低到 2KB 或做分包）。
2. **呈现**：从「预览」改成「**可滚动阅读**」。480×320 在 12px 下约 37 字/行 × 18 行 ≈ 660 字/屏，最长的一条要 3~4 屏。
3. **emoji**：GB2312 没有 emoji，现在 NR 子流程整段剥掉。但这些 emoji 承担了**状态色**（🔴🟢🔵🟡、✅❌），剥掉后「主卧：🔴 门关」变成「主卧： 门关」，信息反而含糊。建议映射成彩色圆点。

### 11.3 三种呈现方案

**A. 列表 + 详情（推荐）**
通知页 = 8 条标题列表（标题 1 行 + 相对时间 + 未读点），点击进详情页看全文（纵向滚动），左上角返回。
- 长文完整可读；条数多时一屏能扫到 8 条标题
- 代价：多一层页面（详情页），触摸点选区要留够

**B. 单条全屏 + 上/下切换**
默认显示最新一条全文（可滚动），底部三个小按钮：上一条 / 下一条 / 最新。
- 一眼就看到内容，层级最浅
- 代价：与四键 TAB 抢底部空间；切条全靠点按钮，条数多时烦

**C. 卡片流**
纵向滚动的卡片列表，每张 3~4 行预览，点开展开全文。
- 最接近手机通知中心的观感
- 代价：控件数量最大，滚动 + 展开两套交互都要调

### 11.4 排版适配注意

- **两列表格（音量说明 / 房间情况）在比例字体下对不齐**。屏幕侧只能左对齐顺序排，建议发送端改单列，或退化成「休息模式 低档 · 静音」这种一行一条。
- 保留 `【】` 分段（字库已含【】），段首用圆点或竖线弱化层级。
- 相对时间「1分钟前」由设备端按 ts 计算，比绝对时间省字符也更像通知。
- 「忽略」在屏幕上等价于「删除当前通知」；可放在详情页顶部右侧或底部。

### 11.5 待定（修订版）

1. 呈现方案选 A / B / C
2. emoji：映射彩色圆点 / 直接剥掉 / 只映射状态色那几种
3. 单条上限：4KB 全文 / 2KB 折中（超长截断）/ 保持 460B
4. 要不要「清除」动作（删当前条 / 清空全部）
